# 联盟职位后续修改设计

状态：已完成代码实现与离线验证（2026-11-17，北京时间 21:06 后开始）。未连接真实账号执行验证，未重启现有脚本；新逻辑在用户自行重启后加载。

## 修改前已定位的问题

- `src/server.mjs` 在连接时读取盟主身份，手动刷新成员也会更新 `guildRoleCanManage` 并触发初始化，但没有处理协议已有的 `SCGuildMemberTitleChange` 推送。
- `src/guild-role-page.mjs` 每三秒只读取机器人状态，没有同步成员职位和管理权限。
- `desiredTitles()` 每次以最初的职位快照作为运行目标，临时副盟退出后，之前为其让位的原副盟可能被升回。随机逻辑主要用于最初选择给永久副盟让位的人。
- 配置保存接口在已有活动快照时拒绝修改永久副盟名单；保存后也没有独立的动态名单应用流程。

## 一、盟主身份自动检测

1. 托管连接建立后查询一次身份；监听 `SCGuildMemberTitleChange`、联盟变更及入盟/离盟事件，推送到达后合并重复通知，经账号只读调度通道核对身份和完整成员列表，职位写操作进入账号串行工作队列。
2. 后台每约 15 秒做一次低频核对作为漏推送的兜底，不依赖职位页面是否打开。断开或暂停托管后停止轮询和职位写操作。
3. 首次确认成为盟主后，先持久化原始 R2/R3/R4 职位快照，再初始化永久副盟。重复推送、刷新页面和重连不得覆盖未恢复的原始快照。
4. 初始化期间，在指令时间窗内的有效消息可以按原规则入队；永久副盟初始化完成后再执行。失去盟主身份立即关闭指令执行，保留恢复所需记录。
5. 页面接收后台职位状态变更通知，重新同步成员职务、管理按钮和初始化状态；另保留低频只读同步与手动刷新兜底。同步不覆盖未保存的表单草稿。
6. 初始化或职位调整后重新读取成员列表，不能把操作前的旧列表返回给页面。

## 二、运行中副盟空位保持空着

- 原始职位快照只承担最终恢复职责，不再用于每轮重新填满副盟。
- 活动开始时保留原本在任的副盟；为永久副盟或有效临时指令让位后，记录其已经让位。
- 临时副盟主动下位或 120 秒到期后，执行下位并释放空位，不主动升回原副盟，也不随机找人补满。
- 此后只有最新页面永久名单的晋升需求，或有效的排队“上副盟”指令，才能占用空位。
- 下位后按精英优先和实际精英名额分配 R3；没有精英空位则为 R2。当前精英最多 20 人、副盟最多 4 人。
- 原副盟让位后，如在允许指令名单内，也可以重新发送新的“上副盟”指令参与排队；不能因其原始快照为 R4 就拒绝所有后续申请。

示例：原副盟甲为临时副盟乙让位，乙到期后空一个 R4；甲不会自动升回。下一条有效上副盟指令或待处理的永久副盟申请可以使用该空位。统一恢复时，甲才按原始快照恢复 R4。

## 三、永久副盟名单在运行时间窗内动态应用

- 沿用页面“永久副盟（最多 2 人）”成员选择器，以成员 ID 保存，显示昵称。勾选和取消后短暂合并连续编辑，自动保存到后台。
- 后台校验成员、最多两人的限制及配置版本，先持久化最新期望名单，再安排账号串行队列应用变化。后台运行依据已经保存的配置，不依赖浏览器持续打开。
- 页面分别显示“已保存”和“职位已生效/等待空位/应用失败”。保存成功不等于游戏职位操作成功；服务端回读确认后才显示生效。
- 新增成员：如果已经是临时副盟，将其转为永久管理并取消对应到期计时，不重复升职；否则有空位就晋升。
- 移除成员：取消永久身份，在有效应用时段内执行下副盟，按精英优先和容量落到 R3 或 R2，不自动给该成员生成新的 120 秒临时租约。
- 更换两人时先处理移除项释放名额，再处理新增项；连续编辑按最新已保存版本合并，不执行过期名单。
- 新增永久副盟且满员时，优先使用本次移除的永久副盟释放的空位；其次可让非永久、没有有效临时租约的在任副盟让位，并记录让位状态。初始化时仍可随机选择足够数量的非永久原副盟让位。
- 已采用的满员策略是保留已发放临时副盟的有效租约：如果满员者全部属于永久名单或未到期临时副盟，新增永久成员等待到期/主动下位后的空位，并优先于新的普通晋升申请。页面标记“等待空位”。等待期间不抢占有效临时租约。
- 永久名单优先于普通聊天租约：普通上下副盟指令不改变成员的永久身份；永久成员退出通过页面取消。已排队的旧指令执行前重新核对最新名单。
- 动态上下永久副盟使用已有的 `commandStart` 至 `commandEnd` 时间窗，同时校验本地和服务器时间。时间窗外可提前修改并保存名单，留到下一次有效活动应用；停止接收新指令后至统一恢复前，不再因名单编辑发起新的永久副盟升降，已有租约到期和恢复照常执行。
- 首次接管盟主时仍按原有规则，在保存快照后完成永久副盟初始化；若已到统一恢复时刻，恢复优先，不再开启本日新一轮初始化。活动结束后的名单编辑仅作为后续预配置。

## 四、配置与活动状态的保存

继续使用每个账号现有的联盟职位配置文件，不另建仅存于浏览器的永久名单。

| 数据 | 保存与读取方式 |
| --- | --- |
| 允许发指令名单 | 保存到账号配置文件，后台从配置加载 |
| 精英优先名单 | 保存到账号配置文件，沿用现有活动期间修改限制 |
| 永久副盟名单 | 同样保存到配置文件；运行中保存后刷新后台配置，并在有效时段应用差异 |
| 转让目标与统一恢复后转让开关 | 保存到配置文件，恢复完成后使用当时有效配置 |
| 原始职位快照、临时租约、运行中职位目标与让位记录、已处理及待处理的永久名单、指令去重记录 | 保存到活动状态文件，重启后核对实际游戏职位继续处理 |

动态保存应只更新永久名单对应字段，防止页面中的旧完整配置覆盖允许名单、精英优先或转让目标。使用现有配置版本校验，多页面修改冲突时提示重新同步。

恢复执行开始后冻结本次转让目标；如果转让前目标被修改或取消，停止旧转让并重新核对最新配置。结果未知时先查询，不盲目重复转让。

## 五、完整执行顺序

托管连接 → 自动核对盟主身份 → 保存一次原始职位快照 → 初始化永久副盟 → 执行时段内队列与永久名单变更 → 副盟下位留下空位 → 到恢复时间严格按最初快照恢复 R2/R3/R4 → 确认全部恢复成功 → 按保存的设置转让盟主。

统一恢复不考虑永久副盟名单，也不按运行中让位结果恢复；手动恢复具有相同含义。恢复和转让期间停止新的晋升，避免名单编辑、队列及收尾操作交错。未确认恢复完成前不得转让盟主。

## 六、实施范围与验证

- 身份监听与页面同步尽量放入独立模块，在已有服务器连接、断开和页面通知处增加少量接入点，减少后续合并上游的冲突。
- 调整机器人目标职位计算，持久记录运行中的让位和下位，原始快照保持不变。
- 为永久名单增加独立的保存和应用流程，解除现有永久名单运行中禁止修改的限制，保留精英优先的现有限制。
- 验证无需打开网页即可接管、重复推送不重建快照、原副盟不补位、永久名单实时增删、临时转永久不被旧计时器下位、满员等待策略、消息顺序与单次执行、配置冲突和重启恢复、严格恢复后再转让。

## 八、2026-11-18 手动恢复后转让

- 转让按钮在有活动快照时也可使用，确认时说明先恢复后转让；不要求先关闭机器人或单独点击恢复。
- 同一账号的串行任务先校验本次目标与昵称，再使用专门的收尾恢复通道恢复原始快照并回读，最后转让。本通道允许恢复写操作，同时停止普通指令和永久名单初始化。
- 手动目标优先于本次活动的自动转让配置；恢复期间不触发另一个配置目标。恢复失败保留快照和恢复状态，不执行转让，后续补偿恢复也不误触发旧自动目标。
- 无快照且无临时租约时可直接核对并转让；重复提交被拒绝，连接或身份变化会停止后续操作。
